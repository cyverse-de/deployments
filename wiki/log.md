# Wiki Update Log

## 2026-08-05

* **New**: [Permissions Performance Testing](/playbooks/permissions-performance-testing.md) — `synthesize-perf-dataset.sql` and `benchmark-permissions-lookup.sql`, which build a production-sized dataset in the permissions schema and measure the group-expansion paths against it, so scale can be tested without copying real user data onto a workstation. The row counts are the easy part; three shape properties decide whether the result means anything, and getting one wrong produces a reassuring benchmark of nothing. de-users must hold essentially every user, since one enormous group is what makes an expansion expensive. Ownership must be skewed rather than uniform, or the planner gets statistics it never sees in production. And nesting must be disjoint rather than chained — an early version chained consecutive groups, so each absorbed the whole tail below it and the closure came out at 102,082 against production's 54,467. Measured: the shipped inlined expansion runs in 5 ms at production scale, the capped `expand_groups` path in 58 ms, and `recompute_group_closure` for de-users in 427 ms, which is what every membership write to that group costs. Recorded honestly that the synthetic data does **not** reproduce the 2.6x improvement measured against real production data — both query shapes land within noise here — so it confirms the shipped query is fast without confirming the comparison.

* **Update**: [groups](/services/groups.md) — the service now honors the public marker when authorizing a group read, and the page explains it. A public team or community carries a `read` grant held by `GrouperAll`, and Grouper's privilege engine resolved that subject as everyone. `requireReadOrMember` only asked whether the *acting user* held read, with group expansion — and no user ever expands to `GrouperAll`, which has no members and no groups row — so the grant was never consulted and every public group became unreadable to non-members. Grouper returned the group with an empty member list where this returned 403, so the browse-teams flow worked against Grouper and broke against this service, across roughly 183 public teams and 55 public communities. The marker is now checked as itself, without expansion, between the acting-user check and the membership fallback. Two traps recorded alongside it: `GrouperAll` never appears in `grouper_memberships_v` because that view is membership while the marker lives in the privilege fields of `grouper_memberships_all_v` — checking the wrong one makes the grant look inert — and a group's permissions resource is named by the group's external 32-hex id, so a grant recorded against anything else authorizes nothing, including for the owner. Also recorded a deliberate widening: Grouper gave public teams `viewers` but not `readers`, so non-members saw the team with an empty member list, and since the importer collapses both to a single `read` grant a public team's membership is now visible to any user.

* **Update**: [groups](/services/groups.md) — a public group's member list is no longer public by default, restoring a distinction Grouper made and the migration had flattened. Grouper separated `viewers` (discoverable and joinable) from `readers` (membership listable), giving public teams the first and public communities the second; both import as the same `GrouperAll` read grant because the permissions service has no level weaker than read, so honoring the marker alone published the membership of all ~183 public teams. `groups.members_public` (migration `000055`) carries the difference, defaulting to false so migrating cannot publish a membership that was not already public. The importer derives it from `readers` and replaces the whole set each run so a revoked privilege reverts; terrain sets it at creation from `public_privileges`. The member list of a public-but-not-members-public group is served as **200 with an empty list** rather than 403, because that is what Grouper did and the DE's team page renders from it — refusing would break the page for every public team, which is the symptom that prompted the change.

* **Update**: [Permissions Performance Testing](/playbooks/permissions-performance-testing.md) — corrects an earlier claim on this page that the `GrouperAll` grant was a display marker conferring no access. It was reached by checking `grouper_memberships_v`, which is membership and never contains `GrouperAll`; the grant is a privilege field and does confer read. See [groups](/services/groups.md).

* **Update**: [Permissions Performance Testing](/playbooks/permissions-performance-testing.md) — records that a group's resource is named by its external 32-hex id rather than by anything derived from its name, since that is what the groups service passes to the permissions service when authorizing. The generator named them `perf-grp-<n>` at first, so no grant was ever findable and every synthetic group's own owner got a 403 on it. Also records that the `GrouperAll` read grant marking a public team or community is a display marker only and confers no read access, because `GrouperAll` has no members for a user to expand to — verified as pre-existing rather than a migration change, since Grouper's own `grouper_memberships_v` never reported it among a user's groups either. The visible consequence is that opening a team you neither own nor belong to returns 403 even when it is marked public, from a listing that shows every team regardless of access.

* **Update**: [Permissions Performance Testing](/playbooks/permissions-performance-testing.md) — records a standing schema gap found while building the above: `permissions.permissions` has no index with `resource_id` leading, only `(subject_id, resource_id)`, so the foreign-key check behind `ON DELETE CASCADE` from `resources` scans the whole table once per deleted resource. Clearing 1.49M resources did not finish in ten minutes; with the index it took 3.7 seconds. It predates the groups work — the table comes from migration `000021` — and belongs in a migration rather than in a test script.

* **Update**: [groups](/services/groups.md) — added `terrain_groups_backend`, which selects whether [terrain](/services/terrain.md) reads groups from Grouper or the groups service, rendered as `terrain.groups.backend`. The template previously rendered no `terrain.groups.*` at all, so the only way to flip terrain over was to rely on its compiled defaults — which meant the toggle that is terrain's rollback path was not expressible from the inventory. The default stays `iplant-groups` so no shared environment flips by inheriting it. Recorded the precondition that matters: the deployed [apps](/services/apps.md) image must tag communities by ID first, because the new backend does not block community renames and an older apps orphans every tag on the first rename with nothing raised anywhere. Also recorded the two response shapes that change on the flip — `display_name` becomes the short name rather than the full colon-delimited Grouper path, and `id_index` goes empty — both of which a caller consumes without erroring, which is what makes them worth stating in advance. Group IDs are unaffected, so permission grants and iRODS `@grouper-<id>` names survive the switch.

## 2026-08-04

* **New**: [Rewriting App Community Tags](/playbooks/community-tags.md) — `community_tags.yml` and the `community-tags` command behind it. An app's community tag was the community's *name*, composed by the browser and stored verbatim, so renaming a community dropped every app tagged with it out of its own listing with nothing raised anywhere — which is how production came to hold 17 tag values naming communities that no longer exist. The rewrite is a command rather than a migration because the mapping spans two databases: community identity is in the permissions schema of the DE database and the tags are in the metadata service's own, so no migration in either can see both. It must run after the group import, which is what records the `legacy_name` the mapping joins on. Orphans are reported and left alone; a value already holding an ID is skipped, which is what makes a second run a no-op.

* **Update**: [Importing Groups from Grouper](/playbooks/grouper-import.md) — the "no longer in Grouper" report now separates groups Grouper lost from groups created natively, which is not a distinction it could previously make. apps creates `workshop-users` lazily against whatever store it points at, so from the moment apps cuts over a healthy deployment grows groups Grouper never had, and every subsequent import reported them as having disappeared — sending an operator after a deletion that never happened and burying a real one in the noise. `legacy_name` already told them apart, since the importer records the Grouper name on every group it writes. Found by deploying apps against the groups service locally: the first request to `/admin/groups/workshop` created the group, and the next import called it missing.

* **Update**: [group-propagator](/services/group-propagator.md) and [apps](/services/apps.md) — both now read groups from the [groups](/services/groups.md) service, so their `iplant_groups.*` config sections become `groups.*` and `baseurls_groups` joins the common defaults. Two defects surfaced while repointing group-propagator, both of which produce wrong iRODS ACLs rather than errors. Its nested-group expansion recursed on the member's *name*: that works against iplant-groups only because a group member's name is its full colon-delimited Grouper path, which doubles as a lookup key, and the groups service names a group by its short name. Both backends have served membership by ID all along, so keying the recursion on IDs works against either. Its periodic crawl also listed groups in one unpaginated request, which the groups service caps at 1000 against production's 2,583 — it would have propagated the first page and silently ignored the rest, the same silent-truncation shape that made the abandoned Keycloak design unworkable. For apps, the community-admin check now accepts `own` as well as `admin`: the importer only ever produces `admin` for a community, but a community created natively grants `own` to its creator, and filtering on `admin` alone would lock that person out of tagging apps into their own community.

## 2026-08-03

* **Update**: [Importing Groups from Grouper](/playbooks/grouper-import.md) — added a section on testing the importer against a local cluster, and `ansible/scripts/seed-local-grouper.py` to make that possible. A freshly deployed local DE has one DE group and two LDAP subjects, which proves the importer runs and nothing about whether it is correct. The seeder creates every group type with owners, a two-level nesting chain, a member reachable by two paths, and the privilege vocabulary including `GrouperAll`, going through iplant-groups rather than the Grouper database so the groups are formed the way the DE forms them. Records what to look for in the report — the closure line is the informative one — and how to tell convergent from merely idempotent by mutating Grouper between runs. Notes the trap that a rename must come back as `1 updated` with nothing reported as missing from Grouper, which is what demonstrates the importer matches on the Grouper UUID rather than the name; matching on the name would detach every permission held against a renamed group.

* **Update**: [Local Single-Node Deployment](/playbooks/local-single-node-deployment.md) — the advertised API address is now pinned, and there is a repair script for clusters where it has drifted. Left unset, k0s re-detects `spec.api.address` at every start from the default route and bakes a DHCP lease into the component kubeconfigs and the `kubernetes` Service endpoint. When the lease moves the cluster goes half-down rather than down: kube-proxy and CoreDNS lose their watches and keep serving what they already programmed, so everything older keeps working while anything created or redeployed afterwards is silently never programmed — a new Service does not resolve, a redeployed pod is healthy but its ClusterIP does not route, and nothing reports an outage. `bootstrap-local-k0s.sh` now writes `/etc/k0s/k0s.yaml` before installing, pinning the address to `10.255.255.1` on a dummy interface that a systemd unit brings up ahead of `k0scontroller` — an address belonging to no physical network cannot move, and being identical on every workstation means runbooks can name it. Three alternatives were rejected for reasons worth keeping: the LAN address is the lease this exists to avoid, a VPN address only exists on machines running that VPN and so cannot be assumed across a team, and the kube-bridge address is created by the CNI, which cannot start until the node has registered with the API server, so advertising it deadlocks a fresh install. `repair-local-k0s-api-address.sh` diagnoses read-only by default and repairs with `--fix`; it edits the address in place when the config exists rather than regenerating it, since writing default CIDRs over a running cluster's would renumber it. This is the server-side half of a problem the bootstrap script already handled for clients by rewriting the kubeconfig to `127.0.0.1`.

* **Update**: [Keycloak](/infrastructure/keycloak.md) and [groups](/services/groups.md) — the groups service now has a Keycloak client, and the page records which of `keycloak_config`'s three service-account role lists to use. The distinction is where a service logs in: terrain's admin client is in master because terrain builds its token URL against `realms/master` by name, while groups logs in against the DE realm and queries it, so its client belongs there. `view-users` is a client role of the built-in `realm-management` client rather than a realm role, so granting it through the realm-roles list matches nothing and leaves a service account that authenticates and then 403s on every lookup — a failure that reads as a bad secret. Also recorded that the groups deployment carries the `de_ca_*` partials because its Keycloak call is HTTPS, that the Grouper importer deliberately carries none (postgresql with `sslmode` disabled and plain HTTP to permissions, so no TLS at all), and that `GET /` reports both dependencies.

* **Update**: [vice-operator](/services/vice-operator.md) — `vice_operator_ca_bundle_configmap` now records which images can honour it. Merging `main` took the app-exposer and vice-operator build descriptors back to the `v2026.08.04` release, which predates the CA-bundle merge (app-exposer PR #164), so the flag the role renders does not exist in the image it pins: the operator exits at startup on an unknown flag and crash-loops. Nothing here is wrong for QA or production, where `de_ca_bundle_configmap` is empty and the flag is never rendered, but a deployment with a private CA sets it and gets a failure whose message names neither the release nor the variable. The page previously described the flag as unconditionally available.
